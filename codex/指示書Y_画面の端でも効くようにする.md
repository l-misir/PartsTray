## 1. ユーザーの言葉と、なぜ起きるか

- 11/21：「いろんなアプリで一番端まで判定がない（エクスプローラーとか Acrobat のタブ切り替え、VS Code のスクロールバー）のがありますが、端にあるのに端まで判定がないスクロール系はなんとかできないですか？」。Claude が 3 案を出し、ユーザーは **1 と 2** を選んだ（3 のクリックをずらすのはしない）
- 最大化した窓でも、多くのアプリはスクロールバーやタブの外側に数ドットの縁を残すので、画面の端に押し付けたカーソルは、その縁の上にある

## 2. やること

### 2.1 高速スクロールの判定を端まで広げる（案 1、既定でオン）

- カーソルが**そのモニターの端から数ドット以内**（右端・左端・上端・下端。数は 2 ドット）にあり、カーソルの下の窓が**最大化している**（またはそのモニターいっぱいに広がっている）とき、スクロールバーの見分け（昔ながら → Chromium の右端 → UI オートメーション）を、**端から内側へ最大 8 ドット（DPI に合わせる）ずらした点**でも試す。どれかで見分けられたら「スクロールバーの上」
- ずらす向きは、カーソルが張り付いている端から画面の内側へ。縦のスクロールバーの判定なので、主に右端（左端も、右から左の窓のため）
- 設定 `wheel.edgeAssist`（既定 true）で切れるようにする。設定画面の「ウィンドウ・ホイール」にチェック（説明：「画面の端にカーソルを押し付けても、少し内側のスクロールバーで高速スクロールにします」）

### 2.2 ホイールを数ドット内側に届け直す（案 2、既定でオフ）

- 設定 `wheel.edgeRedirect`（既定 false）。設定画面に「画面の端で回したホイールを、少し内側の部品に届け直す（試し）」のチェック。説明：「Acrobat のタブなど、画面の端の少し内側にある部品にホイールを届けます。届け直しを受け付けないアプリもあります」
- オンのとき：カーソルが**モニターの端から 2 ドット以内**で、カーソルの下の窓が最大化しているとき、ホイール（縦・横）をフックで取り込み、**端から内側へ最大 8 ドット（DPI に合わせる）ずらした点にある子の窓**（`WindowFromPoint` / `ChildWindowFromPointEx`）へ、`WM_MOUSEWHEEL` / `WM_MOUSEHWHEEL` を `PostMessage` で届け直す（lParam はずらした点の画面座標、wParam は元の delta とキーの状態）
  - ずらした点の窓が、カーソルの下の窓と同じ（縁がない）なら、届け直さずにそのまま通す
  - 高速スクロール（2.1）に当たったときは、高速スクロールを優先する
  - Chromium の作りの窓（`Chrome_RenderWidgetHostHWND`）・管理者の窓（PartsTray がふつうの権限のとき）・自分の窓には届け直さない（通す）
  - フックの中では窓を探す重い処理をしない。今の「判定用のスレッドで調べて覚えておく」作りに乗せ、覚えた結果だけをフックで使う。覚えていなければ通す
- 初めて届け直したら、記録に 1 回だけ（窓のクラス名は書いてよい。題名は書かない）

## 3. テスト
