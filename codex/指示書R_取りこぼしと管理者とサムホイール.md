## 1. 右ボタンを離したのを取りこぼすと、ふつうのスクロールで切り替わる（不具合）

11/21 の実機の記録：右ボタン＋ホイールの押下が 20 秒近く続いたあと「ボタン解放の取りこぼし: 古い記録を破棄して新しい押下を処理」が出ていた（2 回）。その間、ユーザーは右ボタンを押していないのに、スクロールしただけで窓が切り替わった。取りこぼしたのは、管理者で動いているタスクマネージャーが前面にいたとき（ふつうの権限のフックには、管理者の窓が前面の間の入力が届かない）と考えられる。

- ホイール（縦・横）が来たとき、エンジンが右ボタンを押している途中だと思っていても、**実際の右ボタンが離されていたら**（`GetAsyncKeyState`。左右のボタンを入れ替える設定 `SM_SWAPBUTTON` なら物理の左を見る）、その押下を「よそで離された」として終える：クリックの再送もジェスチャーの命令もしない、軌跡・吹き出しを消す、右ボタン＋ホイールの集計を記録に書く。そのホイールは取り込まず、ふつうに通す
- マウスの移動でも同じ確かめをする（フックが重くならないよう、確かめるのは右ボタンを押している途中のときだけ）
- エンジン（`PartsTray.Core`）に「よそで離された」の入口を作り、OS の確かめは `PartsTray/GestureModule*.cs` 側でする（エンジンは OS に触れない）

## 2. 管理者として動かす（設定でオン、既定はオフ）

ユーザーの言葉：「管理者権限で実行するようにしたい」（タスクマネージャーなど管理者の窓も切り替え・ジェスチャーの対象にするため）。配った人の PC では今までどおり、ふつうの権限で動く。

### 2.1 設定と起動

- 設定 `runAsAdministrator`（`AppSettings` の分かりやすい場所。既定 false）と、設定画面のチェック（自動起動の近く）。説明文の例：「タスクマネージャーなど、管理者で動いているアプリの窓も、切り替えやジェスチャーの対象にします。オンにすると、起動のたびに Windows の確認（UAC）が出ます。自動起動はタスク スケジューラーを使うので、ログオン時には出ません」
- 起動したとき、設定がオンで、今が管理者でなければ、同じ exe を `runas` で起動し直して（`ShellExecute`、引数で起動し直しだと分かるようにする）、今のほうは終わる
  - UAC で「いいえ」が押されたら（エラー 1223）、ふつうの権限のまま動き続け、記録と通知で知らせる
  - 1 つしか動かない仕組み（`Program.cs` の Mutex と、2 つ目の起動で設定画面を開く EventWaitHandle）：起動し直す前に Mutex を手放し、新しいほうは数秒だけ Mutex を待つ
  - 管理者で動いているときに、ふつうの権限で `PartsTray.exe` をもう一度起動したら、今と同じく設定画面が開くこと。管理者のプロセスが作った Mutex・イベントは、ふつうの権限からは開けない（整合性レベル）ので、ふつうの権限からも「待つ」「知らせる」だけはできるセキュリティ（低い整合性ラベルなど）を付けて作る
- 設定画面でオンにしたときは、その場で起動し直すか聞く（「今すぐ管理者として起動し直しますか？」）

### 2.2 自動起動

- 設定がオンのときの自動起動は、HKCU の Run ではなく **タスク スケジューラー**（ログオン時、今のユーザー、最上位の特権）を使う。Run は管理者のアプリを起動しないため
  - タスクの名前は `PartsTray`。XML で作り、`schtasks /Create /XML … /TN PartsTray /F` で登録する
  - 既定の条件に注意：**電池で動いているときも起動する・電池になっても止めない**（`DisallowStartIfOnBatteries`・`StopIfGoingOnBatteries` を false）、**実行時間の上限なし**（`ExecutionTimeLimit` を `PT0S`）、複数起動しない
  - 作業フォルダーは exe のフォルダー
- 自動起動の切り替え（通知領域のメニューと設定画面）は、設定に合わせて Run とタスクのどちらかだけを使い、もう片方は消す。タスクの登録・削除は管理者で動いているときしかできないので、ふつうの権限のときにタスクを消す必要があれば記録に書き、次に管理者で動いたときに片付ける
- 今の `MigrateAutoStart`（古い場所からの引っ越し）の動きは壊さない

### 2.3 管理者の窓の扱い

- PartsTray が**ふつうの権限**で動いているときは、管理者で動いているアプリの窓を切り替えの候補から外す（元に戻す・前面に出すが効かず、そこで止まるため）。見分け方：プロセスのトークンの昇格（`TokenElevation`）を調べ、開けない・読めないときも管理者とみなす
- PartsTray が管理者で動いているときは、外さない

## 3. サムホイールで切り替え（Options+ が動いている間）

11/21 の実機の記録：キーのあとの選ぶ時間・右ボタン＋ホイールのどちらでも「横 0 回」。Options+ が動いている間、サムホイールの横スクロールはフックから見えない方法で送られている。ユーザーの言葉：「一応横スクロールでも反応するようにして。使いづらかったら無くしましょう」。

- `GapSession` は、Options+ が動いている間もサムホイールの回転の知らせ（HID++ の THUMB_WHEEL 0x2150、function 0、先頭 int16 BE が回転量）を受け取っている（今は「サムホイール回転を検出: PartsTray は送信しない」と記録するだけ）。これを外に知らせる口（イベント）を作る。肩代わり中（Active）の自分の横スクロールの仕組みは変えない
- 選ぶ時間の間（`WindowKeysModule`）と、右ボタン＋ホイールの押下中（`GestureEngine`）に、この回転を横のホイールとして数える。回転量は `ThumbWheelConverter` で速さ 100%・向き 1 として delta に直し、`reverseHorizontal`・`wheelSwitchStep` は今の横のホイールと同じに使う
- **二重に数えない**：ある選ぶ時間・押下の中で HID++ の回転を 1 回でも受け取ったら、その間のフックの横ホイールは取り込むが数えない
- Options+ の横スクロールそのものは止められない（切り替えと同時に、カーソルの下の窓が少し横にスクロールする）。これはユーザーに伝えてあり、了承済み
- スレッド：`GapSession` の知らせは HID のスレッドから来る。`WindowKeysModule` には UI のスレッドへ、`GestureEngine` には今のエンジンの呼び方の決まりに従って渡す（別のスレッドから直接エンジンを呼ばない）
- 設定 `windowKeys.thumbWheelFromDevice`（既定 true）で切れるようにする（「使いづらかったら無くす」ため）。設定画面の「ウィンドウ・ホイール」にチェック
- 記録の集計（「横 n 回（合計 d）」）に、HID++ から数えた分も入れる。生の回転量の合計も記録に出す（実機で量を合わせるため）

## 4. テスト

- §3：HID++ の回転が選ぶ時間・押下の中で数えられ、外では数えられない。二重に数えない。`thumbWheelFromDevice` がオフなら数えない。`GapSession` の今の動き（肩代わり中の横スクロール）が変わらない
