## 修正 1（重大）：無効ウィンドウのドラッグ中に、カーソル移動を握りつぶしている

- `GestureEngine.Handle` の Move で、`Phase.Drag` のとき `return true` している。WH_MOUSE_LL で WM_MOUSEMOVE を握りつぶすと、**カーソルそのものが動かなくなる**
- さらに、次のイベントの座標は「止まったカーソル位置＋その回の移動量」になる。そのため、`Origin + (現在位置 − 押下位置)` が 1 回分の移動量にしかならず、ウィンドウが元の位置の近くで震えるだけになる
- 対応：ドラッグ中の Move は **素通し（false）** にし、MoveWindow の発行だけを行う。左ボタンの押下と解放は、今までどおり握りつぶす
- テスト：`DisabledWindowDragUsesCachedOriginAndSuppressesRelease` を直す。Move は false を返すこと。複数回の Move で、ウィンドウの位置が `Origin + 累積の移動量` になること

## 修正 2（重大）：解放を取りこぼすと、古い記録が残り続ける

- `buttons[]` の記録は、解放を受け取ったときにしか消えない。Windows は、時間のかかったフック呼び出しを飛ばすことがある。フックが外されて付け直す場合もある。どちらの場合も、解放はフックを通らずにアプリへ直接届く
- 記録が残ると、次に同じボタンを押したとき、`buttons[b] != null` なので押下は素通しになる。ところが、その解放は古い記録の段階に従って握りつぶされる。その結果、**相手のアプリでボタンが押されたままになる**。古い記録が「ストロークありのジェスチャー」なら、関係のない次の解放で**コマンドが実行される**
- 対応：
  1. Down を受けたとき、同じボタンの記録が残っていたら、取りこぼしとみなして古い記録を片付け、ワーカー経由で警告をログに残す。そのうえで、新しい Down を通常どおり処理する
     - 片付けの内容：pending から外す。右ボタンなら TrailEnd を出す。コマンドも送り直しもしない
     - ただし、古い記録が `Replaying`（押下の送り直しが、まだ完了していない）なら、その押下の後に解放を 1 回送り直して釣り合わせる（理由: 本物の解放は先にアプリへ届いているため）
     - `Passed` は何もしない（本物の解放はアプリに届いている）
  2. 生存監視でフックを付け直すときは、`SetPaused(true)` → `SetPaused(false)` ではなく、新しいメソッド `HookLost()` を呼ぶ。`HookLost()` は、すべての記録と pending を**送り直しもコマンドもせずに**捨て、TrailEnd を出す（理由: フックが無い間の入力は、アプリに直接届いているため。ここで押下を送り直すと、押されたままになる）
- テスト：
  - 右 Down → 解放なし → 右 Down → 動かさずに Up：2 回目の押下と解放だけが、この順で 1 回ずつ送り直されること。1 回目からはコマンドも送り直しも出ないこと
  - ストロークのある有効なジェスチャーの途中で解放を取りこぼす → 次の右クリック（動かさない）でコマンドが実行されないこと
  - 中央 Down → 判定が「タイトルバーでない」→ 押下の送り直しが未完了（Replaying）のまま、中央 Down が来る → 古い押下の後に解放が 1 回送り直され、その後に新しい押下が処理されること
  - `HookLost()` の後、`Passed` だったボタンの解放は素通しになること。送り直しが 1 つも出ないこと

## 修正 3（高）：スクロールバーの判定を、最上位ウィンドウにだけ送っている

- `Probe` は、WM_NCHITTEST をトップレベル（root）にだけ送っている。標準のスクロールバーの大半（リストビュー、ツリービュー、エディットなど）は、**子ウィンドウの非クライアント領域**にある。トップレベルはそこで HTCLIENT を返すので、ほぼ検出できない
- 対応：
  - `WindowFromPoint` で得た一番奥の子ウィンドウ（child）を判定の対象にする。子が無ければ root になる
  - child のスタイルに WS_VSCROLL（0x00200000）があるときだけ、child へ WM_NCHITTEST を送り、HTVSCROLL（7）かどうかを見る。WS_VSCROLL が無いウィンドウには送らない（理由: ブラウザや WinUI のアプリにまで、別プロセスへのメッセージを 30 ms ごとに送らないため）
  - クラス名 "ScrollBar" で SBS_VERT の子ウィンドウの判定は、今のままでよい

## 修正 4（高）：カーソルが止まると、100 ms でキャッシュが古くなる

- 判定の依頼は、カーソルが動いたときにしか出ない。そのため、**カーソルを止めてから 100 ms たつと、キャッシュは必ず古くなる**。実際の操作では、ユーザーはスクロールバーやタイトルバーの上でいったん止まってから、ホイールやクリックをする。このままでは、高速スクロールも無効ウィンドウの移動も、ほとんど働かない
- 対応（「100 ms 以内・同じ位置」という使う側の条件は変えない。キャッシュを新しく保つ側を足す）：
  - 最後のカーソル移動またはホイールから **3 秒間**は、カーソルが止まっていても、`Tick` が判定の依頼を出し続ける。間隔は 50 ms で、30 ms の下限は守る
  - ホイールを受けたときも判定の依頼を出す（30 ms の下限は守る）。これで、止まって 3 秒以上たってから回し始めても、最初の 1 ノッチは通常のスクロールになり、2 ノッチ目からは高速スクロールになる
  - 3 秒を過ぎたら依頼を止める（理由: 何もしていないときに、別プロセスへの問い合わせを続けないため）
- テスト：
  - カーソルを止めたまま 1 秒たっても、依頼が続いていること（50 ms 間隔）
  - 3 秒を過ぎると依頼が止まること
  - 止まって 3 秒以上たった後のホイールは素通しになり、そのホイールで依頼が出ること

## 修正 5（高）：フォーカス移動を、UI Automation の部品単位で行っている

- いまは、ホイールの 1 ノッチごとに、カーソル下の UIA 要素へ `SetFocus` している。ブラウザや最近のアプリでは、**リンク・ボタン・入力欄にフォーカスが移ってしまう**。その結果、フォーカス枠が出る、ページの onfocus 処理が動く、フォーカスした要素が見える位置まで自動でスクロールしてユーザーのスクロールとぶつかる、といった副作用が起きる
- さらに、この処理は判定スレッドを最大 200 ms 止める。その間、右クリックの判定が待たされ、軌跡の表示が遅れる
- かざぐるマウスのこの機能は、**ウィンドウ（HWND）単位**でフォーカスを合わせるものである。そこで、仕様を次のように確定する：
  1. child ＝ WindowFromPoint の結果。クラス名が "ScrollBar" または "SysHeader32" なら、その親を使う
  2. root ＝ GetAncestor(child, GA_ROOT)。root がフォアグラウンドでなければ何もしない
  3. child == root なら何もしない（理由: ブラウザや WinUI のように HWND が 1 つのアプリでは、合わせる対象が無い）
  4. GetGUIThreadInfo で、root のスレッドの hwndFocus を調べる。それが child か、child の子孫なら何もしない
  5. child が無効または非表示なら何もしない
  6. それ以外のときは、AttachThreadInput(自分, 相手のスレッド, true) → SetFocus(child) → AttachThreadInput(…, false) を実行する。失敗はログに残す（同じ内容の連続は抑える）
- 実行場所：**専用のスレッド**で行い、判定スレッドは一切待たない。前の処理が終わっていなければ、新しい依頼は捨てる（相手が応答しないときに積み上がらないようにするため）
- フォーカス移動の処理から UI Automation の使用をやめる。エクスプローラの選択中の項目の判定（UIA）は、今のままでよい

## 修正 6（小）：UI Automation の最初の呼び出しが遅い

- UIA は、プロセスで最初に呼んだときの初期化に数百 ms かかることがある。そのため、起動直後にエクスプローラで右ドラッグすると、50 ms の判定が間に合わず、ファイルの右ドラッグがジェスチャーになってしまう
- 対応：起動時に、選択判定のスレッドで `AutomationElement.RootElement` を 1 回取得して暖機する。待たずに投げるだけでよい
